# 002. Первое настоящее сообщение через Kafka

## Было / стало

- Было: `8132885` — Trade Event Flow существовал только как заранее описанная анимация.
- Стало: `18fec16` — отдельное Spring Boot-приложение публикует реальную запись и ждёт её получения через Kafka.

Сценарий `001` доказал только наличие Kafka-компонентов в Spring context. В
`002 Trade Event Flow` мы впервые проверяем всю цепочку.

После нажатия Play медиатор запускает изолированный Spring context. В нём находятся
собственные `TradeFlowPublisher`, `TradeFlowListener` и tracker. Они не используют
компоненты первого сценария, поэтому эксперимент можно изменять и ломать, не
затрагивая уже работающий пример.

Client создаёт команду. Publisher формирует событие с уникальным `eventId` и
отправляет его через `KafkaTemplate` в `scenario-002-trade-events`. Завершение
send future означает, что Kafka приняла запись и вернула metadata: partition и
offset. Это уже позволяет честно подсветить broker и topic зелёным.

Kafka показана контейнером, а topic — внутренним квадратом. Такая вложенность
подготавливает следующие сценарии: позднее внутри topic появятся partitions, а
для кластера можно будет показать несколько brokers и replicas.

Listener получает записи через `@KafkaListener`. Старые записи не считаются
успехом: tracker ждёт именно `eventId`, созданный текущим запуском. Если
acknowledgement или подходящее событие не появляется за десять секунд, соответствующая
часть схемы получает статус `FAILED`.

Runtime log и анимация отображают уже подтверждённые факты: команда доставлена,
Kafka вернула partition/offset, listener получил совпадающее событие.

Практический вывод: успешный `send()` ещё не доказывает end-to-end доставку. Он
подтверждает запись в Kafka, но отдельно необходимо наблюдать обработку consumer-ом.
