# 001-a. Почему визуализатор постоянно опрашивал backend

## Было / стало

- Было: `f8fdc4d` — браузер каждые 500 мс запрашивал runtime и повторно создавал SVG.
- Стало: `e73162c` — один long-poll запрос ждёт новую revision, и экран обновляется только после изменения.

После запуска первого сценария обнаружилась проблема: браузер каждые 500 миллисекунд
вызывал `GET /api/scenarios/runtime/active`, даже когда ничего не происходило.
Получив тот же ответ, JavaScript снова перерисовывал SVG.

Такой подход называется short polling. Он прост: клиент периодически спрашивает
сервер, появились ли изменения. Для прототипа это удобно, но постоянные запросы
создают шум, а лишняя перерисовка может мешать взаимодействию с графом. Например,
во время перемещения ноды весь SVG может быть создан заново.

Есть три соразмерных способа исправить ситуацию. Можно оставить short polling,
но сравнивать состояния и вызывать `render()` только при изменении. Можно перейти
на long polling. Третий вариант — открыть постоянный поток Server-Sent Events,
через который backend сам будет отправлять обновления.

Следующий шаг — long polling. Браузер отправляет запрос, а backend не отвечает
сразу. Он ждёт появления нового runtime-события или истечения timeout. Получив
ответ, клиент обновляет экран и немедленно открывает следующий ожидающий запрос.
Когда событий нет, бессмысленного обмена сообщениями почти не происходит.

Для текущего состояния проекта long polling — разумный вариант:
он работает поверх обычного HTTP, не требует WebSocket и хорошо показывает
модель ожидания изменений. Серверу при этом понадобятся версия runtime-состояния
и механизм ожидания без блокировки servlet-потока, например `DeferredResult`.

Для большого постоянного однонаправленного потока событий Server-Sent Events был
бы естественнее: backend держит соединение и отправляет события сам. Но сейчас
проблема некритична, сценарии запускаются редко, а отдельный streaming-контракт
усложнит небольшой прототип. Поэтому применяем long polling, а SSE сохраняем как
понятную точку роста, если количество событий и пользователей увеличится.

Практический вывод: polling удобен для прототипа, но частота запросов не должна
подменять модель событий. Интерфейс стоит обновлять тогда, когда состояние
действительно изменилось.
